# Changelog

All notable changes to this project are documented here.

## [Unreleased]

- **The second question before the spindle or the laser goes on:** when a job that goes on after a stop waits with `pause.power_on`, the screen says that continuing again switches the spindle or the laser on, in the eight languages. It needs a server with that question. Host-tested only.

- **Safety: Continue and "Tool changed" answer the question on the screen.** The screen sends back the identifier of what the job asked when the button was pressed (`pause.question`), so a server that asks something else by then refuses the answer (`409 question_changed`, with its text in the eight languages) instead of taking it as the answer to a question nobody has read; the buttons are drawn again as soon as the question changes. The copy of the settings contract has the new setting `answer_needs_question` of the server (106 settings). A server of an earlier version is answered as before. Checked by the host tests; not tried on a screen.

- **Safety: the screen says that the spindle is started when a job goes on.** While a job that goes on after a stop waits before its first move, the job page warns that letting it go moves the machine back to where it stopped and starts the spindle the program had on.
- **The reason of a resume the server does not do is shown:** a `422 bad_request` of `resume-from` shows the reason of the server on the screen, not only that something was wrong.
- **The copy of the settings contract follows the server:** 105 settings in 17 groups, with the settings of a stop and of going on, and millimetres and micrometres written as `mm` and `µm`; the fonts hold the characters of the new texts.

## [0.1.2] - The settings of the server drawn from its contract and its light view of the values in force, a login for the touch screen and the newest refusal codes in eight languages

- **The settings of the server are shown with their values in force to a login that is not an administrator:** `core/settings_values.hpp` reads the light view (`GET /api/v1/settings/values`, any login: the `hmi` application of an operator included, a few kilobytes and never more than 16 KiB) and the page draws the values with the labels and warnings of the copy the screen carries, read only. An administrator still reads the full contract; one whose token cannot read it falls back to the light view. Until now these logins saw the copy with no value at all.
- **`ETag` and `304`:** the link sends the tag of the last answer in `If-None-Match` and keeps the page when the server answers `304` (a few bytes instead of a few kilobytes); the tag is forgotten when the login changes or a read fails, and a header that is not a tag (a quote inside, a space, more than 100 characters, a break of line) is never sent or kept. The sockets keep 16 KiB for this route and report an answer over it as too long.
- **The page says when its copy of the contract is out of date:** the generator writes the SHA-256 of the contract it was made from (`kContractCopyHash`) and the page compares it with the `contract_hash` that the server gives in the light view and in the full contract; when they differ it warns that texts and keys may be out of date. A hash that is not 64 lower-case hexadecimal characters says nothing.
- **A secret and a path of the computer are never shown:** a key the server marks secret, or whose value is the mark `***`, is Hidden whatever the server sent in its place and no value is kept; a key whose value the server keeps back (`hidden`) says so; a value the server cut ends with an ellipsis; a key the copy does not know is drawn read only even when its value is kept back.
- **An answer that cannot be trusted is not drawn:** a key that is not a name of lower-case letters, digits and underscores, an entry that is not an object, a value that is an object, a text or a list over the limits, more than 256 keys, a count that is not the number of keys, an answer cut short or nested too deep ends as the copy of the screen with the reason in the language of the operator.
- **New lines in `hmi.cfg`:** `settings_values` (on) and `settings_values_poll_s` (30, 5 to 3600), with their ranges in `hmi.cfg.example`, in the self-test and in the README tables.
- **Three more sentences of the page in the eight languages of the tables:** where the values come from, a key the server does not show and the contract that is not the copy; the other 29 languages show the English ones.
- **112805 more checks in `test_settings`:** the light answer as the server writes it, the page of the light view in the eight languages, the `ETag` and the `304` against a simulated server, the header of the answer, who reads what (administrator, operator, viewer, unknown role, a token without the scope, the setting off, no login, an older server), the answers that go wrong, hostile documents, the file lines, a seeded storm of roles and failures and a seeded bending of the answer.

- **The settings of the server are drawn from its contract:** `core/settings_contract.hpp` reads `GET /api/v1/settings/contract` (the 89 settings in 15 groups of EH3D-SERVER, each with its type, range, default, unit, whether it applies at once or after a restart, the route that writes it, the role it needs, its risk and its label, help and warning in eight languages) and `core/settings_page.hpp` turns it into the block "Server settings" of the settings page: the value in force of each setting, the ones that are not the default in amber, a switch as On or Off, a number with its unit, a secret as "Hidden" (it is never asked for or shown). The link reads the contract after the first reading of the fleet and then every `settings_poll_s` seconds.
- **A copy of the contract travels in the screen:** `core/settings_contract_gen.hpp`, written by `tools/gen_settings_contract.py` from `docs/settings-contract.json` of the server (texts in the order of the tables of the screen, a document of another schema, a missing text or a route other than `PUT /api/v1/auth/policy` for a policy key is refused). When the live contract cannot be read (the login is an operator, nobody answers, the answer is too long, the schema is newer, the answer is not a contract) the page shows the copy, read only and without values, and says why in the language of the operator. `--check` fails when the file is not the one the server gives.
- **What the screen does not know is read only:** a key the live contract has and the copy lacks is drawn from the live contract, a key with a value and no entry is a read-only line with its name, a type it has never heard of is a read-only line, a group the contract does not list goes last, and a schema of a newer version is not drawn at all (the copy is shown). The page counts the keys the copy does not have.
- **The screen changes no setting unless `hmi.cfg` says so:** a change needs the live contract, the route `PUT /api/v1/auth/policy` and no other, a login as an administrator (the login now keeps the role the server gave it; a screen that uses the static `token` never learns its role), `settings_write = on`, the key in `settings_write_keys` and no job running (`settings_block_running`). The 70 settings that are set in `server.cfg` are shown and never written; a secret is never shown, asked for or written.
- **A change is asked step by step:** the question is in the words of the setting, a risky one shows its warning and asks a second time, a value the server calls looser than recommended (`409 weak_confirm_required`) is asked about a third time and sent with `confirm_weak`, each question has its own time and gives up by itself, and a spoken order never starts a change. What is typed is checked against the contract before anything is sent (type, range, length, choices). The answer is read by code (saved, saved after a restart, refused with the text of the code in eight languages, nothing sent); an answer of 200 that is not the JSON of the server is not a saved change.
- **New lines in `hmi.cfg`:** `settings_contract` (on), `settings_poll_s` (600), `settings_write` (off), `settings_write_keys` (none) and `settings_block_running` (on), with their ranges in `hmi.cfg.example`, in the self-test and in the README tables of the eight languages; a line that cannot be used changes nothing.
- **Warnings where the server and `hmi.cfg` disagree:** the page warns when `rack_max_slots` of the server is below the highest place of `rack_places`, and the core has the sentence for a file larger than `max_body_mb`.
- **The sockets keep up to 1 MiB for the contract:** the answer is some 250 KB, over the 256 KiB kept for any other answer, which would have made the live contract unreadable.
- **The table of the refusals of the server is up to date:** `core/server_errors_gen.hpp` has 151 codes (143 before); three codes of the server (`bad_bgcode`, `bambu_lan_off`, `bgcode_unsupported`) still have no eight texts in the table of the phone app and are shown as their code.
- **Texts of the page in the eight languages of the tables:** `core/settings_text.hpp` (35 sentences, the same holes in every language, formal register in German, French and Portuguese); the other 29 languages show the English ones, and a Japanese or Chinese text is drawn only when its characters are in the fonts of the screen.
- **Tests:** a new host test program, `test_settings` (29279 checks, with a seeded storm of failures against a simulated server and 300 bent documents), covers the copy (89 settings in 15 groups, 19 through the policy and 70 in the file, every one with its texts and a control), the copy written as the server writes it and read back by the code of the live answer, the documents the screen does not understand, the control and the checks of each type, who may change what, the steps of a change, the answers by code and the texts; `tools/test_gen_settings_contract.py` tests the generator. The READMEs state the counts of the programs as they are measured.
- **Documentation:** `docs/SETTINGS_CONTRACT.md` says what the screen shows, which keys it may change and why none by default, the lines of `hmi.cfg` and what has not run; the file tree and its picture, the tables of the READMEs, the checklist of the hardware day (five new steps) and the notes on the profiles are brought up to date.
- **The check of the two screens is up to date:** `tools/profile_parity_baseline.json` no longer lists the differences that were closed when the Bungard repository took the login, the table of refusals and the keyboards from this one, and `tools/check_profile_parity.py` passes again.

## [0.1.1] - Login as the hmi application, refusal codes in eight languages, plugin machines in the fleet list and the Bungard screen as a profile

- **The Bungard screen is this screen plus a profile:** `profiles/bungard.cfg` holds the settings that EH3D-NODE-BUNGARD-HMI carries on top of the generic ones (`machine_kind`, `tool_bar`, the `jog_*` panel and `clock_utc_offset_min`), `docs/PROFILES.md` says what is shared, what a profile is and what is still written only in the other repository, and `tools/check_profile_parity.py` (with `tools/profile_parity_baseline.json`) compares the two repositories when they sit side by side: the shared files must be the same text once the names are made equal, and the generic settings plus the profile must be the settings file of the Bungard screen. Its tests are in `tools/test_check_profile_parity.py`.

- **The screen logs in to the server as the application `hmi`:** with `server_user` and `server_password` in `hmi.cfg` (the password is write-only and never shown or logged) the link logs in with `POST /api/v1/auth/login` once the health check found an EH3D server, keeps the token of the login, renews it with `POST /api/v1/auth/refresh` when it is in the last quarter of its life, and forgets it when any request comes back with 401, so the next round logs in again. A refused login waits 30 s, 60 s, 120 s... up to 10 minutes before the next one, and the login never goes to an address that did not answer the health check. Without a name and a password nothing changes: the `token` of the settings is used. `core/session.hpp` holds the rules (host tests in `test_session`); `GET /auth/sessions` and the closing of one login are read and built there, with no page to show them yet.
- **The refusals of the server are told by code in the eight languages of the tables:** the notes of the screen show the text of the code of `{"error": ...}` in the language of the operator (143 codes, generated by `tools/gen_server_errors.py` from the codes of EH3D-SERVER and the texts of the phone app, so the screen, the app and Studio say the same words); a code the table does not have is shown as the code and its detail. The other 29 languages show the English text. A text with a character the fonts of the screen do not hold (most of the Chinese and Japanese ones until the fonts are built with them) is not drawn: the English text is shown instead.
- **Settings of the connection:** `server_timeout_s` (1 to 120, 15) is how long one try of a request may take, `server_retries` (0 to 5, 2) how many more tries follow a failure on the network, with waits of 200 ms, 400 ms, 800 ms... up to 2 s. A connection that could not be made is tried again for any request; a time-out or a broken connection only for GET, HEAD, PUT, DELETE and OPTIONS, and a 502, 503 or 504 likewise, so a request that creates something (a job, a start, a login) is never sent twice. The stop keeps its own short time-out and its own tries. `server_mdns` (off) is read and kept; this screen has no resolver yet, so the address is `server_host`.
- **The machines of the plugins are on the fleet page:** the screen reads `GET /api/v1/work/machines` (at the first reading and then every fifth) and shows each machine with its state and the plain entries of its `detail`, the ones that raise an alarm first; a machine with `latched`, `estop_latched` or `alarm` on is drawn in red with the warning mark. A server that does not give them (403 or 404) shows none.
- **The host tests and the checks of the settings know the new keys:** `test_session` (4132 checks) covers the login and its renewal, the tries again, the connection settings, the table of the refusals and the machines of the plugins; the keyboard table, `tools/selftest.py` and `hmi.cfg.example` carry the five new keys, and `tools/test_gen_server_errors.py` checks the generator of the table. Nothing has run on the screen or against a real server.

## [0.1.0] - Newest improvements of the screen interface of the node

- **The stop of the screen no longer waits in the queue of the touches, and it is tried again:** the touch of the stop sets a flag that the task of the stop reads, so it cannot be lost when the queue of eight is full (a touch of anything else that does not fit now says so); when the server cannot be reached the note stays and the stop is tried again every `stop_retry_ms` (1 second) up to `stop_retries` (10) more times, both in `hmi.cfg`. The host tests cover the flag and the plan of the retries.
- **After a health check that found nobody, or something that is not an EH3D server, the link sends nothing with the token or a body:** only the health check and the stop (always tried) go out, so a job file, a start or the token do not reach whatever answers on the address.
- **A number of the server is brought into range before it becomes an integer:** `percent`, the counters of a job, the tool, the limits of the spindle, the clock and the other whole numbers read from the answers of the server go through `Json::int_in(key, lo, hi)`, so a value such as `1e99` or an infinite one gives the end of the range instead of an undefined conversion; a host test covers it.
- **The token of the server no longer goes with the health check:** the first request after a start or a lost link is sent without the `Authorization` header, so whatever answers on that address does not receive the token before it is known to be an EH3D server.

- **The stop no longer depends on the last reading of the fleet:** a stop from the touch screen, the voice or the hardware input now sends the stop of the machine (`POST /machines/:id/stop`) first, which needs no job id, and keeps the cancel of the job the fleet shows and of the job of this screen as a backup for a server without that route. A job another program started after the last reading, or a fleet that could not be read, is now stopped; before, the screen said there was no job to stop, or cancelled an old job, got a refusal that it took for success and left the machine running. Covered by the workflow host test; not tried against a real server from the screen.
- **Simulation of the server for the screen:** add `tests/test_sim.cpp`, a program that runs the screen against a simulated EH3D-SERVER in memory (one machine, one job that stops when it is told to) that can be made to fail: no answer, a router page, a missing token, a 503, an answer cut short and a degraded server. The screen is driven with its own requests, its own reading of the answers and its own state of the link and the age of the data, with the clock as a number; a seeded storm of 300 failures checks that the state of the link is always the one of the cause and that the same seed gives the same run. 1824 checks. The manifest now says `evidence: simulator`. Nothing has run on the screen (the Guition 10.1" with the ESP32-P4 and the ESP32-C6) or against a real server.

- **The CI validation checks the workflows and the lessons of past CI failures against a baseline:** `tools/workflow_hygiene.py` and `tools/lessons_lint.py` (copies of the shared tools) run in the validation, and only findings that are not in `tools/workflow_hygiene_baseline.json` and `tools/lessons_lint_baseline.json` fail it, so what exists today stays as it is and a new one is caught. `python tools/workflow_hygiene.py --root . --detail` and `python tools/lessons_lint.py --repo .` list the findings.
- **The validation of the CI is the reusable one of the documentation hub:** the job `validate` calls `validate.yml` of EH3D-DOCS (pinned by commit) and what the repository checks besides it is in jobs of their own, with the check of the CHANGELOG.

- **The settings file is tested damaged:** `test_hmi` reads the settings file cut at every place and in 600 copies with bytes changed, inserted or cut (a fixed seed), and no value ever leaves its range. The counts of the host tests in the README are the ones of the CI.

The fonts are built from the literals of both screens, in GitHub Actions, with `lv_font_conv` 1.5.3 and the fonts of LVGL 9.3.0 (`EH3D_EXTRA_LITERALS` in `tools/make_locales.py` names the other screen's file).
- **The screen says when the server answers but is not well:** the health check tells `degraded` and the note `ui.SrvDegraded` is shown, in the 37 languages.

- **The first request to the server is its health check:** after a start or when the link was lost the screen asks `GET /api/v1/health` (open to anyone, no token goes with it) and tells "nobody answers" from "something answers that is not an EH3D server" (`classify_health` in `core/server_link.hpp`) before it asks for the fleet.
- **The host tests also run under AddressSanitizer and UBSan in the CI:** the same programs are built with `-fsanitize=address,undefined` and run (an undefined behaviour stops the test), and `test.sh` / `test.bat` run the same steps as the CI (the repository checks, the tests of the tools, the pictures and the languages, and the host tests).

## [0.0.6] - Screens that tell the operator what happens

- **The sentence for a machine without a spindle is translated:** `ui.WhyNoSpindleHere` was missing from the 27 locale files and showed in English; it is now written in all of them, the exception for it is gone from `tools/make_locales.py` and `test_locales`, and a missing key in any language (the two variants excepted) fails `make_locales.py --check` and the new `tools/test_make_locales.py`.
- **Robustness settings:** `sdkconfig.defaults` turns on the task watchdog (reset on a hang, both idle tasks watched), raises the stack of the main task above the default, and turns on the stack overflow canary and the FreeRTOS stack data. The firmware logs the stack each task has left (`HMI_STACK_REPORT_S`, `HMI_STACK_WARN_BYTES` in the menu) and warns when one is short. `tools/check_firmware_defaults.py` (with `tools/task_needs.py`) guards these settings and the stack of each task, and its tests run in the CI. Not built or run on a module; the stack numbers are to be tightened after a run on the board, and an old `sdkconfig` in a build folder must be deleted for the new defaults to apply.
- **The screen says what is wrong with `hmi.cfg`:** a line that cannot be used is shown under the top bar (the line, the key and why, in the language of the operator, with how many more there are) instead of being ignored in silence, and a missing file says so. The reason of every problem is now a code (`CfgReason`) next to its English text for the log.
- **The server is checked at the start:** no `server_host` or no answer on the port (`18200` by default), or an answer that is not from an EH3D server, shows a clear note with the address once, when the state changes.
- **The connection state is always visible:** the top bar says connected, no connection or other server (an answer that is not an EH3D fleet, or a server that does not list the machine of the settings), and the data are marked old, with their age, when the server has not updated them for `stale_after_s` seconds (new setting, 15 by default, 2 to 3600); the list of machines turns amber and each row says `Old data`.
- **The confirmation counts down and speaks the language of the operator:** the dialog shows the seconds left before it aborts by itself (`confirm_timeout_ms`) and names the order (`Stop the machine`, `Start the job`, `Jog X -`, `Spindle 12000 rpm`) in the 37 languages instead of the internal id.
- **No more English literals in the notes of the screen:** the notes of the application (stop sent or not sent, file chosen, nothing to send, going on from the holes done...), the reasons of the job workflow, the errors of the connection and the names of the orientations and of the spindle choice are texts in the 37 languages; 52 new texts in all, with the fonts built again for the characters they need.
- **The position bar no longer shows invented numbers:** it shows dashes until the position is read from the machine.
- **Version on the screen and name in every request:** the firmware version is on the title bar and in the settings, and every request to the server carries `name/version` in the headers `User-Agent` and `X-EH3D-Client` (`client_id`, `wire`).
- **Tests:** new `test_status` (the report of `hmi.cfg`, the link and the age of the data, the notes, the order and the countdown, the identification of the client), the keys and texts in `test_locales`, the age setting in `test_status`, and `tools/test_check_firmware_defaults.py`. The firmware has not been rebuilt with this change.
- **A self-test for the day the screen meets the hardware:** `tools/selftest.py` checks `hmi.cfg.example` (or `--cfg FILE`) with the rules of the firmware, starts a toy server on port 18200 and checks that its answers are what the screen's parsers need; with `--server HOST:PORT` it asks a real server the same questions with GET only. It writes `selftest_hmi-gui_<time>.txt`, sends nothing to hardware and never prints the token. Its tests run in the CI.
- **`docs/HARDWARE_CHECKLIST.md`:** the steps to do by hand on the screen, with what must happen and where to write the result.
- **`hmi.cfg.example` is read by the screen:** the explanations moved to their own lines, because a comment after a value is part of the value and made the screen reject the line.

## [0.0.5] - Start, pause and stop that work, G-code, and warnings of the board and of the job

- **A board larger than the table is warned about:** choosing a drilling or routing file on the card compares the size of its box (the holes, or the moves of the pen) with the table of the machine - the course that the server reports less the offset, read from the configuration file of the machine, or `table_width_mm` and `table_depth_mm` of `hmi.cfg` when the server does not say it - and a board that fits neither lying nor turned is warned about on the job page with its size and by how much it goes over. The job is not blocked: the server refuses what lies outside the table.
- **A job that was cancelled or failed is not a finished job:** the screen says which of the two it was, with the reason of the server, never marks it as finished, plays no notice of the end for it and does not forget it before the server has said how it ended; it is kept to go on from the holes already done. A job that left the machine and whose end the server has not yet told is neither finished nor stopped.
- **The notes of the server about a job are shown:** what a job asks for beyond the spindle of the machine (turns or feed above or below what it holds) is listed on the job page when the job is made.
- **Texts:** one new text for the board that does not fit and one for a failed job, in the 37 languages, and the fonts built again for the characters they need.
- **Tests:** `test_workflow` grows with the box of drilling and routing files, the board that fits, fits turned and does not fit, the table from the configuration of the machine, the cancelled, failed and finished jobs, and the notes of the server; `test_hmi` with the two new settings.
- **The screen looks for the server on port 18200**, the port the server listens on, in the default and in `hmi.cfg.example` (it was 8080, so a configuration that only named the host never reached the server).
- **Starting a job works:** the start of a job that is ready no longer waits for an armed link (a job is armed only once it runs, so the start was always refused). It has its own kind in the gate: it still needs the stop released and the hardware stop wired when the setting asks for it, and it asks for the confirmation like a move; the question is no longer dropped while the link is not armed. With the bench setting that turns the question off, the order now goes at once instead of doing nothing, and a start with no job ready says so before asking anything.
- **Pause holds, it no longer cancels:** the pause button asks the server to hold the job (`POST /api/v1/jobs/:id/pause`) and a new button lets a held job go on (`/resume`); the pause is never held back by the gate. The server holds only G-code jobs, so for a drilling or routing job its reason is shown on the screen and the job keeps running.
- **Tool change:** while a job waits at a tool change, a new button ("tool changed") answers it through the gate and sends the confirmation to the server.
- **The stop goes first:** the stop has a task of its own, no longer a place in the queue behind other requests, with a short timeout and three tries; it cancels the job the fleet shows on the machine (also one started from another program or screen) and the own job when it is another one. If it could not be sent the screen says so. Pressing the hardware stop sends the same stop to the server, once for each press.
- **Texts:** one new word (tool changed) in the 37 languages and the fonts built again for the characters they need. The spoken order for a pause is now a pause, and the one for a start is a start.
- **Tests:** `test_hmi` grows with the start of a ready job through the gate (and its confirmation while the link is not armed), the pause that is never held back and the press of the hardware stop as an edge; `test_workflow` with the pause, the release of a held job, the tool change as the only thing `confirm` answers, and the requests of a stop (fleet job, own job, both, none). The firmware has not been rebuilt with this change.
- **G-code programs from the card:** the screen now sends `.nc`, `.gcode` and `.tap` files to the server as a G-code job (`job_gcode_request`), on its own and never paired with a drilling or routing file; the server judges the program against the machine and its reason is shown when it refuses. The start goes through the gate, the pause and resume are the server's, a stopped program goes on through `resume-from` from the lines already done (counts shown without a unit), and there is no file to send again for a program, so an old server cannot resume one. The firmware has not been rebuilt with this change.

## [0.0.4] - Resume a stopped job through the server

- **Going on after a stop through the server:** EH3D-SERVER keeps the request of every job and makes the new one itself (`POST /api/v1/jobs/:id/resume-from`, with `skip` brought forward and the tools off kept), so the screen asks for that instead of sending the file again (`job_resume_from_request`, `Workflow::resume_request` and `on_resume_from`). A job that was stopped goes on even after a reset of the screen (it follows the job again and has no file) and without the file on the card. The new job is only made ready (`resumed_from` is shown on the job page), it waits for the operator, and the start goes through the gate as any other, with the spindle turns cut to the limit. A server that does not have the route (404 or 405, but not the 404 of an unknown job) is remembered as an old one and is answered as before with the file the screen keeps; a refusal of the server (`409 not_stopped`, `422 no_work`) is shown with its reason, and a second touch while the answer is awaited does not make a second job. A job followed again after a reset now also knows from the server whether it was a drilling or a routing job (holes or cuts).
- **Texts:** one new word in the 37 languages (resumed from) and the fonts built again for the characters they need.
- **Tests:** `test_workflow` grows with the new job made by the server (also after the second stop, after a reset and for a routing job), the 409, the 422, the 404 of an unknown job, the old server (404 and 405) with the fallback to the file, an old server with no file, an answer with no job, and the link that fails. The firmware has not been rebuilt with this change.

## [0.0.3] - Tools of the file, spindle limit of the server, resume and the job in two programs

- **The gate keeps to the spindle:** a spindle order carries the turns it asks for (the new setting `spindle_rpm`, 12000 by default, is what the spindle button asks), and the gate never lets it ask for more than the lower of `spindle_max_rpm` and the top speed of the spindle the machine carries, as the server says it. With the new setting `spindle_over = clip` (the default) an order for more is cut to that speed and the screen says so; with `refuse` it is refused with a reason. The confirmation of the spindle shows the turns it will really get, a move is never cut and a stop is never held back. A laser or a pick and place machine still has no spindle: its order is refused and its screen has neither the button nor the choice.
- **The tools of the file, and the spindle of the machine:** the job page reads the drilling or routing file that is chosen, shows its tools and how many holes or cuts each has, and a tap on a tool switches it off for the job (`skip_tools`); the page also shows the spindle the machine carries, as the server says it. This is the same code as EH3D-NODE-BUNGARD-HMI.
- **A stopped job goes on:** when a job leaves the machine the screen asks the server how it ended; a job that was cancelled or failed is shown as stopped with the holes (cuts) it did, and a button sends the same file again with `skip` set to those already done, so only the rest is drilled or routed. The tools switched off stay off and the start goes through the gate like any other.
- **Drilling and then routing:** a drilling file and a routing file chosen one after the other are two programs of one job: when the server says the drilling is done, the routing is made and waits for the operator to start it, and the job page names the program that comes next.
- **Texts:** the words for holes and cuts and five new ones (the order was cut to the top speed of the spindle, the refusal of an order beyond it, resume, stopped, next) in the 37 languages, and the fonts built again for the characters they need.
- **Tests:** the host tests of the sibling screen for the spindle limit, the tools, the report of a job, `skip`, resume and the chain of the two programs. The firmware has not been rebuilt with this change.

## [0.0.1] - A touch screen for CNC machines, lasers and pick and place machines, on the hardware of the Bungard screen
